# wr-ask-first 提示词清单

先质疑挑坑，再问透立据

按步骤把灰框里的提示词复制给任意 AI，把【方括号】里的内容换成你的实际需求。小改动（改错字、修一行明确报错）跳过本清单直接改即可。

## 一、动手前搜齐 10 个开源方案并挑本机技能

```text
我要做的事是【一句话描述你要做的事，以及目标运行环境和协议约束（如闭源商用、安装包体积敏感）】。

动手从零写之前先做两件事。
第一，先查现有工作环境里已经有哪些现成工具或技能可以直接复用，只列真正对口的，不堆无关工具。
第二，联网搜齐 10 个最近两年仍在维护的成熟开源方案（搜不够 10 个如实写出真实找到的数量，严禁编造链接）。列一张对比表，写清每项的下面五项内容。
1. 原仓库链接
2. 许可证及能不能直接用在当前项目
3. 安装包体积与传递依赖数量
4. 近半年维护活跃度
5. 已知坑位和边界限制

最后给出取舍建议，现成轻量好用的直接选；如果现成包太重会把体积撑大，说明如何参考它的测试用例手写精简版并在代码注释里保留原仓库链接。
```

## 二、强制 AI 先当面质疑挑坑（禁止当应声虫）

```text
下面是我的需求草稿，【粘贴你的需求】。

现在先不写代码，也不要夸这个想法好。请你站在严格工程评审的立场，当面给我挑毛病，逐项回答下面这四个问题（没有风险的项也要写出核查依据）。
1. 泄密与权限越界，这里面有没有把密钥、环境变量、本机路径或私密数据漏给外部或日志的风险？
2. 上下文爆炸，按我现在的做法，会不会把大文件、无关工具或长日志全塞进一个窗口导致模型变笨、规则漏看？
3. 需求自相矛盾，我的几条要求之间有没有互相打架、不可能同时成立的地方？
4. 二阶与三阶烂摊子，这个改动落地后，会连带影响哪些已有页面或老用户习惯？三个月后新增数据或排查故障会不会越改越难？

只讲具体隐患和证据，说完等我回应再进入下一步。
```

## 三、决策树逐轮追问并落盘 `docs/SPEC.md`

```text
先别写代码，也别急着列实施清单。把刚才确认后的需求当成一棵决策树，按下面四条一轮一轮地问我。
1. 仓库代码和配置里能查到的事实，你自己去查，不要拿来问我。
2. 每一轮只问前提已经定下来的 2 到 4 个关键问题，依赖这轮答案的细节留到下一轮。
3. 每题编号，附上你推荐的答案和一句理由，我同意就回一个「好」。
4. 全部岔路口都问清、没有一处需要你猜之后，把结论写成一份 docs/SPEC.md，里面写清目标与明确不做的事、开源选型、核心数据结构与互斥状态、边界失败处理、二三阶影响核对、量化验收标准。等我确认可以动工，你再写代码。
```

## 四、方案卡在二选一时掀开隐藏前提

```text
先停下来，别在方案 A、方案 B 和折中版之间打转了。
1. 用一句话写出这几个方案共同默认成立的隐藏前提，并给出一个最小验证动作测它成不成立。
2. 至少拿出一个绕开这个约束的方案 C，和一个直接改写问题本身的方案 D（换个参数名不算新方案）。
3. 对每个方案做一次翻车预演，假设上线半年后出事了，最可能是怎么出的事。
4. 写清楚哪一条可测的实测数据（延迟、体积、错误率）出现，你就立即推翻现在的推荐。
```

## 五、高代价决策交给不同模型盲审

```text
这是一个改错代价很高的决定，【粘贴脱敏后的现状、硬约束与关键代码片段】。
请独立给出你的方案、成立前提和最大风险，不要迁就我目前的倾向。
（提示，把同一段话分别发给两三家不同模型的新对话。拿到各自初稿后，再把彼此的方案匿名互换，要求每条反驳必须附带代码行号、算式或实测数据，未决分歧留给你自己拍板。）
```
