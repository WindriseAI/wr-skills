## 一、交代清楚上下文后下达十倍提速与十倍瘦身目标

```text
我要优化或重构的目标是【描述模块/构建流程/页面，以及当前实测耗时或体积数据】。
必须原样保留的守门功能与接口契约是【列出不能删的功能、权限校验、对外接口与现有测试套件】。

在动手改代码之前，请先做下面四件事并向我汇报。
1. 核实仓库目录和现有调用链，算出硬盘、内存、网络或协议层面的物理下限，告诉我十倍提速或十倍减重的上限在哪里，哪些地方受物理极限约束做不到十倍。
2. 别只在局部循环里微调，直接从并行结构（如多工作树并行、批量化、流式零拷贝、缓存预热）和做减法（删死代码、删冗余包装、删重型依赖）给出十倍级改造方案。
3. 动手前先联网搜【5】个仍在维护的现成开源方案或成熟做法（数量按需要改；搜不够如实报数，不许编造链接；没有联网能力就直说），列出许可证、体量、依赖数、近半年维护状态和坑位对比表。
4. 明确列出本次改造绝对不能碰的四条防作弊红线，等我确认方案后再写代码。
```

## 二、用十分之一时间分路并行跑完长任务

```text
现在有一批原本按顺序做需要【估算串行时间或步骤数】的任务，目标是【描述交付物】。

请按照用十分之一时间跑完的思路重新组织执行，按下面三条给我拆解方案。
1. 先把必须按先后顺序锁定的公共依赖挑出来，其余互不重叠的任务全部改成并行分路。
2. 明确每条并行支线的独占文件白名单、输入输出契约和独立验收命令，确保合入时不互相踩脚。
3. 说明合入后如何做一次全量真路径核验，保证速度翻倍的同时质量零缩水。
```

## 三、用防作弊四条红线审计十倍优化成果

```text
刚才你（或前一个会话）提交了一版性能优化或体积瘦身改动，相关文件是【列出修改文件或 git diff 范围】。

现在请你站在只看事实的严格审稿人立场，对照下面四条防作弊红线逐项核查，并贴出文件行号和实测命令输出。
1. 有没有靠偷删原有功能、跳过权限校验、砍掉加密验签或去掉边界报错来换取速度和体积下降？
2. 有没有硬编码假返回值、空函数占位或提前返回成功来绕过真实计算、磁盘读写或网络请求？
3. 有没有屏蔽慢路径、把核心逻辑全换成 mock 假替身，只跑空壳快路径来刷数据？
4. 有没有删减原有测试用例、加上跳过标记、改弱断言精度、放宽超时阈值，或者跑出 0 条用例假装通过？

最后给出两栏对照结论，第一栏是改前与改后的真实耗时/体积实测对比，第二栏是上述四条防作弊红线的逐条证据。有任何一条踩红线直接判不通过。
```
