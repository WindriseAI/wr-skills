# wr-axiomatic-design

[← 返回 wr-skills](../../README.md) · [English](../../README.en.md#skills)

> 提取功能需求做下三角解耦。在多路并行干活前，先提取独立的功能需求 FR 与设计参数 DP，画出设计矩阵验明无耦合对角阵或准耦合下三角阵，通过重排顺序和抽取唯一真源消掉右上角反向耦合，再拆开并行推进。

**按 Skills 通用格式编写，可用于 Claude Code、Codex、Cursor、Antigravity、claude.ai 等支持 Skills 的 Agent**（各家没有逐一实测）。 用的 AI 不支持 Skill，也可以直接复制 [提示词清单](提示词清单.md)。

## 为什么并行前要先算矩阵

很多团队哪怕给每个代理切了不同的文件白名单，最后合进主分支还是互相报错、改左边坏右边。根因往往不在文件重叠，而在功能之间的参数依赖本身打了死结（右上角反向耦合）。

MIT 工程学者 Nam Pyo Suh 提出的公理设计（Axiomatic Design）把这种依赖摊在矩阵上，让人和 AI 在写第一行代码之前就能一眼看穿哪里会打架。

| 常见架构翻车 | 用 wr-axiomatic-design 之后 |
| --- | --- |
| 界面文案、样式和逻辑各写了一遍同一组状态，改一个参数三处全歪 | 抽取唯一真源（Single Source of Truth）成上游独立模块，下游全改只读 |
| 三个并发代理各有白名单，合并时却发现模块 A 偷偷假设了模块 B 的内部字段 | 画出 `FR × DP` 矩阵，右上角有 `X` 一律先停并发、拆清顺序再开工 |
| 两个都能跑的方案争论半天，最后挑了个要靠人工记十条规矩的复杂方案 | 用第二公理比较实现难度和状态数量，直接选最稳最简单的一版 |

## 三种设计矩阵对照

把每一项功能需求（FR）写成行，把对应的设计参数或实现模块（DP）写成列，存在影响标 `X`，无关标 `0`。

1. **无耦合对角阵**。只有主对角线是 `X`，右上角和左下角全是 `0`。各条线完全独立，随便按什么顺序改、多少人同时开干都不会冲突。
2. **准耦合下三角阵**。主对角线和左下角允许有 `X`，**右上角全是 `0`**。这说明依赖是单向的，只要先定死排在前面的基础参数（例如先锁定纯数据契约和样式底表），后面的模块就能放心并行推进。
3. **强耦合（右上角非零）**。右上角只要出现一个 `X`，就意味着动了后面的设计参数会反过来破坏前面的功能需求。此时严禁直接多路并行。

## 四步消耦合流程

1. **提取 FR 与 DP**。把需求拆成互不重叠的功能目标列表 FR，再为每条 FR 找出唯一主导它的工程载体 DP。
2. **画矩阵判等级**。列出 `FR × DP` 矩阵，检查主对角线右上方有没有 `X`。
3. **两招消除右上角反向耦合**。先尝试同步重排 FR 和 DP 的顺序把 `X` 翻到左下角；翻不过去的真环形依赖，抽出一份上游唯一真源 DP0 让两边同时变成只读下游，再用第二公理挑最简结构。
4. **验明下三角阵再拆开并行**。确认矩阵右上角全部归零，先把上游真源定稿锁定，再交给 `wr-split-work` 开出多棵 `git worktree` 并行干活。

## 安装

只装这一个技能，运行下面这行命令。

```bash
npx -y skills add WindriseAI/wr-skills -g --skill wr-axiomatic-design
```

一键安装全套风起技能，运行下面这行命令。

```bash
npx -y skills add WindriseAI/wr-skills -g --all
```

更多安装方式见 [主说明文档](../../README.md#安装)。
