# wr-axiomatic-design 提示词清单

提取功能需求做下三角解耦

在大型功能拆任务、多代理并发开工前，或者发现模块之间改一处坏一片时，把对应灰框复制给 AI，将【方括号】里的内容换成你的需求或模块列表。

---

## 一、从需求中提取独立的 FR 与对应的 DP

```text
先别写代码，也别急着拆任务。我要做的功能或重构目标是【粘贴你的需求描述或 docs/SPEC.md 摘要】。

请按 MIT 公理设计的做法，先帮我整理两张一一对应的清单。
1. 功能需求清单（FR1, FR2, ...），站在用户视角或系统对外承诺出发，写出最小互不重叠的功能目标，每条只写「动词 + 宾语」，不混入具体技术实现。
2. 设计参数清单（DP1, DP2, ...），针对每一条 FR，列出唯一主导它的工程载体（例如某个纯数据文件、独立模块、配置表或接口）。
3. 检查有没有两条 FR 其实在说同一件事，或者一个 DP 同时被两条无关 FR 拉扯。先拆干净再给我看清单。
```

---

## 二、画出 FR × DP 设计矩阵并判别耦合等级

```text
基于刚才定下的 FR 与 DP 清单，请画出完整的 FR × DP 设计矩阵（行是 FR，列是 DP，有依赖标 X，无依赖标 0），并完成下面三步判断。
1. 明确标出这份矩阵属于无耦合（对角阵）、准耦合（下三角阵），还是强耦合（主对角线右上方存在 X）。
2. 把主对角线右上方的每一个 X 逐条拎出来，说清「改动哪个下游 DP 会反过来破坏哪个上游 FR」。
3. 如果右上角还存在任何 X，明确阻止直接并发开发，并准备进入去耦合调整。
```

---

## 三、消除右上角反向耦合收敛成下三角阵再派桌

```text
上面这份设计矩阵在右上角出现了反向耦合，现在按下面两招把它消掉。
1. 第一招重排顺序，检查是不是单纯因为 FR 和 DP 的排列顺序写反了，尝试同步调换对应的行与列，看看能不能把右上角的 X 全部翻到左下角。
2. 第二招抽取唯一真源，对于调换顺序后仍然互相指着的双向依赖，把共同依赖的事实、常量、状态机或契约抽出来，独立成上游的唯一真源 DP0，让原本互相打架的模块全部改成只读下游。
3. 给出改造后的新 FR × DP 矩阵（确保右上角全为 0），并写出锁定顺序，即哪几个上游真源必须先定稿锁只读，之后哪几条子线可以放进独立 git worktree 同时并发开发。
```

---

## 四、用信息公理对比两个同样满足独立公理的方案

```text
下面这两个架构方案都满足下三角阵或对角阵，不会互相耦合，【粘贴方案 A 与方案 B】。

请按公理设计的第二公理（信息公理）做一次客观对比，回答下面三个问题。
1. 哪一个方案需要的模块数量、状态组合、特殊分支和人工记忆规矩更少？
2. 哪一个方案出错概率更低、更容易被静态检查或几行单测直接验证通过？
3. 给出最终推荐和具体可测的推翻条件，不要写空泛的形容词。
```
