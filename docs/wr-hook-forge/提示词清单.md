高频踩坑写成确定性拦截钩子

当某类低级错误在你的项目里第二次出现时，把对应灰框复制给 AI，把【方括号】替换成你的具体规矩和仓库环境。

---

## 一、把第二次踩到的坑固化成零依赖静态钩子

```text
同一类错误已经让我纠正到第二次了，就是【描述这个反复出现的错误，例如忘同步版本号 / 混进本机绝对路径 / 改坏关键契约字段】。

请不要再往说明文档里加感叹号警告了，把它写成一个可重复运行的零依赖 Node.js 检查脚本，满足下面四条要求。
1. 先确认这条规矩是不是零例外的客观硬条件；列出需要放行的合法白名单（例如示例模板文件、代码块内部）。
2. 只用 Node.js 自带标准库，确保毫秒级跑完、跨 Windows/macOS/Linux 可用。
3. 同时支持 observe（只追加日志到 .wr-hook-observe.jsonl 并返回 0 放行）和 enforce（返回非零退出码并输出精确文件、行号与修复办法）两种模式，默认先设为 observe。
4. 写一个配套自测脚本，分别验证正常样例放行、违规样例在 enforce 下被拦、违规样例在 observe 下放行并留痕。全部跑通后把输出贴给我。
```

## 二、把文档里的几十条规矩瘦身拆分成「文档 + 钩子」

```text
请帮我审查当前的【AGENTS.md 或团队规范文档】，按下面三步整理。
1. 把全部规矩分成两栏，
   - 适合留在文档的软原则（需要看场景权衡的判断标准）
   - 应该写进脚本或 Agent 钩子的零例外硬规矩（路径、凭据、命令、格式、词表、测试覆盖）
2. 给出精简后的文档草稿（只留软原则，变薄一倍以上）。
3. 针对硬规矩列出一张钩子清单，标明每条该挂在 PreToolUse、PostToolUse、Stop 还是 Git pre-commit，以及默认先用 observe 观察档怎么落地。
```

## 三、给已有钩子补上批量包装工具的参数展开检查

```text
检查我现有的钩子脚本【脚本路径】。
如果 Agent 通过批量编辑工具（edits 数组）、批量搜索工具（queries 数组）或并发执行工具（commands 数组）间接读写文件或执行命令，这个钩子能不能抓到？
请补齐递归参数展开逻辑，把工具输入里所有底层文件路径、写入内容和命令行字符串都提取出来，走同一套拦截规则，并补一条嵌套批量参数的单元测试验证拦截生效。
```

## 四、从 `observe` 观察档审计误报，决定是否切 `enforce`

```text
这是过去一周钩子在 observe 模式下记录的日志，【粘贴 .wr-hook-observe.jsonl】。
请逐条归类分析下面三个问题。
1. 哪些是真正该拦下来的违规操作？
2. 哪些是误伤了正常开发动作？需要补什么白名单条件？
3. 补齐白名单并跑通回归测试后，评估现在是否具备切到 enforce 硬拦模式的条件。
```
