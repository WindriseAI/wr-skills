# wr-skeptic-audit 三席物理隔离独立盲审

写代码的会话里装满了一路妥协的理由，自己审自己几乎永远说「没问题」。把验收切给三个彼此隔离的全新会话，各看各的输入，各挑各的刺。

## 第 0 步 首次对齐（每次启用本技能先做）

<!-- wr-onboarding:start -->
先找配置文件 `wr.config.json`：从当前目录逐级往上找，再看用户目录（`~/wr.config.json`）；两份都有时，项目里的字段覆盖用户目录的。

- 读到 `"onboarded": true`，就按里面的字段办事，不再提问，直接往下走。配置里没写的字段按下面各题的默认值理解。
- 没有这个文件，或者没有 `"onboarded": true`，先把下面 8 题一次发给用户，每题括号里是默认值，并说明「回『好』就全按默认」。用户回「好」或只改了其中几题，其余一律按默认。
- 收到答复后，把答案连同 `"onboarded": true` 写进项目根目录的 `wr.config.json`（用户要求全局生效就写 `~/wr.config.json`），已有字段保留不动，写完告诉用户写在哪、怎么改。字段全集和说明见 github.com/WindriseAI/wr-skills 的 `examples/README.md`。
- 用户说「这次先不对齐」，就按默认值办事，不写文件，下次启用时再问。
- 钩子在 `onboarded` 变成 `true` 之前，除了碰凭据和递归强删照样直接拦，其余规则只记录不拦截。

1. 机器与测试环境：只有这一台电脑，还是另有测试机、容器或 CI？跑测试时能不能占用这台电脑的键盘、鼠标和浏览器？（只有一台；耗时长的测试先说预计多久，同意后在本机跑；可以占用）写入 `environment.machine`（`single` / `has-runner`）、`environment.heavyTestsOnMainMachine`（`allow` / `ask` / `deny`）、`environment.quietMainMachine`（`false`）、`environment.remoteHost`（测试机的 ssh 主机名，没有就留空）。
2. 系统与工具：用什么系统和终端？在哪个 AI 工具里用？有没有装 Orca 多代理工作台？（系统、终端和宿主自动探测；Orca 自动探测）写入 `environment.os`、`environment.shell`、`environment.host`、`tools.orca`。
3. 模型与额度：手上有哪几档模型？有没有第二家厂商的模型可以交叉复核？额度紧、一般还是宽松？（只用当前这一个模型；没有第二家；一般）写入 `modelTiers` 四档（全部留空就是单模型模式）、`review.crossVendor`（`false`）、`budget.mode`（`tight` / `normal` / `generous`）。
4. 协作与发布：一个人做还是团队？要不要让 AI 开多个帮手并行？默认分支叫什么？推送、发版和对外提交由谁确认？（一个人；要并行时先问；分支自动探测；推送和发版必须用户确认）写入 `workflow.team`（`solo` / `team`）、`workflow.parallel`（`off` / `ask` / `on`）、`workflow.defaultBranch`、`workflow.branchPrefix`、`workflow.publishConfirm`（`always` / `push-and-release` / `never`）。
5. 回复语言：回复用什么语言？（跟随用户提问的语言）写入 `language.output`（`auto` / `zh-CN` / `en`）。
6. 做事强度：新功能要不要先问清并写规格？动手前搜不搜现成开源方案，搜几个？要不要定十倍目标？（大活才先问并写 `docs/SPEC.md`；搜 5 个；十倍目标只在用户提到性能或体积时提议）写入 `rigor.askFirst`（`off` / `big-only` / `always`）、`rigor.specPath`、`rigor.openSourceSurveyCount`、`rigor.tenX`（`off` / `ask`）。
7. 安全尺度：安全红线用哪一档？有没有额外不许读的目录？（标准档：碰凭据和递归强删直接拦，git 硬重置只提醒；没有额外目录；删除走回收站）写入 `hookMode`（`observe` 起步）、`safetyGuard.profile`（`relaxed` / `standard` / `strict`）、`safetyGuard.extraProtectedPatterns`、`safetyGuard.trashCommand`。
8. 项目类型：这个项目是网页或桌面界面、命令行或库、后端服务，还是官网营销站？有没有线上用户？官网是否允许 AI 训练爬虫？（自动探测类型；没有线上用户；允许搜索爬虫，训练爬虫由用户定）写入 `project.kind`（`web-ui` / `cli-lib` / `backend` / `marketing-site` / `other`）、`project.hasOnlineUsers`、`geo.languages`、`geo.region`、`geo.crawlerPolicy`（`allow-all` / `block-training` / `custom`）。

本技能主要用到第 3 题（`review.crossVendor` 决定三席换不换厂商，`budget.mode` 为 `tight` 时走精简档）和第 8 题（`project.kind` 不是界面类时第一席改看命令行输出与文档）。

## 触发节奏与总原则

1. **大波合齐后集中审一次。** 等一整批功能全部合入集成分支后统一过三席，不搞每改十行来回拉扯审核。
2. **物理隔离，严禁串台。** 三个席位必须是三个全新会话，互相不共享对话记录，更严禁喂入写代码过程的任何辩解、聊天解释或「为什么要这样写」的说明。
3. **默认不通过，凭证据放行。** 任何放行结论必须附真实截图坐标、原句摘录或 `file:line`，没有证据不许判过。
4. **三席全部只读。** 审查席位绝不直接改代码、不提交、不重启服务；问题一次汇总成清单，交回执行方一轮修清。
5. **按条件降级。** 宿主开不了互相隔离的新会话，就把三席提示词分别粘贴到三个新聊天窗口；`budget.mode` 为 `tight` 时走精简档，只跑第三席，或在一个新会话里分三轮依次扮演三席（每轮开头重申只看本席材料）。`review.crossVendor` 为 `true` 时三席尽量换不同厂商的模型，为 `false` 时同一模型开新会话即可。没有集成分支时，第三席取「当前分支相对默认分支」或「本次提交相对上一次提交」的 diff。

## 第一席 新手用户审交互（严禁读源码）

- **喂入材料**仅限真机或无头浏览器实拍截图（宽屏、窄屏、浅色、深色、空态与满载态）、操作录屏或界面状态序列、完成主任务的点击步数记录。**严禁提供任何代码文件、CSS、架构文档或开发者解释。**
- **没有界面的项目**（`project.kind` 为 `cli-lib` 或 `backend`）把材料换成命令行的帮助输出、常见命令的真实运行输出和报错原文，按同样的六项思路审「第一次用的人能不能顺利跑通」。
- **审查身份**是一个完全不懂技术、绝不看说明书、多点两下就嫌烦的普通新手。
- **必查 6 项**见下面清单。
  1. 第一眼 5 秒内能不能看懂这页干什么用、第一步该点哪里？
  2. 完成最核心的一件事要点几步？哪一步多余或绕路？
  3. 有没有文字被截半个字、按钮压在一起、阴影或浮层盖住字、深浅色看不清？
  4. 报错或空状态说不说人话？下一步该干嘛明不明白？
  5. 点错以后能不能一眼找到退回或撤销？
  6. 手机窄屏下有没有横向拖出白边或点不到的死按钮？
- **输出格式**逐条写「截图编号与位置 + 哪里卡住/嫌烦 + 期望怎么顺手」，只挑毛病不夸奖。

## 第二席 老编辑替普通读者把关文案（严禁读源码）

- **喂入材料**仅限从界面、菜单、弹窗、报错提示、帮助页和说明文档里导出的纯文本清单。**严禁提供任何代码文件和实现逻辑。**
- **审查身份**是一位改过大量稿子的老编辑，替从没用过这个产品的普通读者把关。分两遍读：第一遍把自己当普通读者，只圈看不懂、对不上的地方；第二遍换回编辑的眼光，圈读着像机器生成的句子和没核实的夸大。
- **第一遍 普通读者圈的**
  1. 普通人读不懂的技术缩写、英文代码、内部代号或生造概念。
  2. 同一个功能在不同页面换了两种叫法，前后对不上。
  3. 看完还是不知道下一步该做什么的提示和报错。
- **第二遍 编辑圈的**
  4. 读着像机器生成的句子，例如一段话里堆满破折号、先否定半句再翻过来的套路句、硬凑的三连排比、结尾空洞拔高。这些只是常见例子，按项目自己的文风约定判断；项目没有约定时，标准就是「换成同事当面说话会不会这么讲」。
  5. 没核实过的夸大或替用户编造感受（例如没有数据支撑的「极致」「秒级」「十万好评」）。
  6. 能砍掉一半字数说得更直白的按钮、标题和提示语。
- **输出格式**逐条列「原句位置 + 原句摘录 + 毛病类型 + 一句更平实的改法」，改法必须能直接替换原句；不改写没毛病的句子，不写表扬。

## 第三席 资深工程师只读总审（全新只读会话）

- **喂入材料**只给下面四样东西，严禁喂入作者聊天记录。
  1. 用户的原始需求原话；
  2. 唯一规格准数文件 `docs/SPEC.md`；
  3. 集成头相对基线的完整 `git diff`（大改动先看 `--stat` 再按模块分片读）；
  4. 实现方宣称的检查结果与验收单。
- **必查 8 项证据清单**（每项给出 `PASS / WARN / FAIL` 并附 `file:line`，无行号视为未核查）。
  1. **范围与合并安全**，查有没有改到白名单外的文件，合并冲突时有没有悄悄冲掉别人的逻辑。
  2. **契约与权限一致**，查 `docs/SPEC.md` 里的枚举值、字段名、权限表、边界限制与代码逐字对得上吗。
  3. **全仓零死调用**，查改名、换签名或删除的函数、路由、样式类在全仓还有没有遗漏的旧调用。
  4. **测试真伪推演**，对照改动文件查核心分支真有行为测试覆盖吗，有没有源码搜词、吞异常、跑 0 条用例的水测试。
  5. **静态语法与类型**，查语法、类型、Lint、导入路径是否全部干净无报错。
  6. **运行链隐患**，按真实执行顺序顺一遍，查有没有漏写异步 `await`、空 `catch` 吞错误、未清理定时器/监听器、竞态覆盖。
  7. **文档与配置同步**，查对外 README、示例配置、数据计数、版本号是否随改动同步更新。
  8. **残留与安全清理**，查有没有临时调试日志、硬编码本机路径、密钥字面量、未删干净的探针改动或垃圾文件。

## 汇总裁决

三席全部交卷后，把问题合并成一张分档清单交回执行方。
- **阻断项（必须修完复核）**，包括逻辑缺陷、合并误冲、交互死路、截字遮挡、隐私泄露、严重歧义文案。
- **建议项（本轮顺手清）**，包括多余点击步骤、拗口措辞、轻微样式瑕疵。
- **不改项（记录原因）**，明确属于下阶段需求范围的条目。
